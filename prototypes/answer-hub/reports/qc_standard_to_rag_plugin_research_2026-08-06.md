# qc-standard-to-rag-plugin 与主题转写质量研究

报告日期：2026-08-06
研究对象：[Knjss-0508/qc-standard-to-rag-plugin](https://github.com/Knjss-0508/qc-standard-to-rag-plugin.git)
研究方式：只读研究；未下载、安装或执行外部仓库代码。

## 一、结论摘要

本次未能成功访问指定 GitHub 仓库，因此**无法核验该仓库实际的 `SKILL.md`、提示词、知识点结构化字段和校验实现**。报告不会把未经读取的内容描述成该插件的真实设计。

网络访问情况：

1. GitHub 网页搜索和页面读取没有返回可用仓库内容。
2. `git ls-remote` 只读访问失败，Windows Git 返回 `SEC_E_NO_CREDENTIALS`。
3. 提权重试遇到审批服务异常，未继续绕过安全限制。
4. 本机 `.codex`、`.agents` 和当前项目中未找到该插件的缓存或副本。

在这一限制下，本报告完成了两部分可核验工作：

- 根据用户提供的知识导出截图，确认当前主要问题是“正文直接复述个案最终结论、缺少前因后果、推荐回复与正文重复、关联标准项像分类路径而非真实标准库条目”。
- 对当前项目的转写提示词、证据输入、规则降级、标准关联门禁、CZ 同步和自动初标代码进行只读核查，形成可直接实施的优化方案。

核心建议是：

> 不再让模型直接从一组散乱文本生成最终知识，而是先生成“可追溯主题证据包”，再按知识形态生成包含前提、核验过程、结论和适用边界的正文；每个关键事实必须绑定来源记录。当前无标准模式下，新知识的关联标准项必须为空，不能把模型分类、标签或抽象路径写入该字段。

## 二、截图反映的具体质量问题

截图中的知识正文普遍接近以下形式：

```text
某设备出现某现象，该情况应直接判定为某结果。
```

这类内容存在四个问题。

### 1. 缺少前因后果

正文只保留最后结论，没有说明：

- 这个问题在什么业务场景下出现；
- 需要先确认哪个对象、部位、型号或代际；
- 结论成立依赖哪些现象、测量结果、查询结果或图片条件；
- 采用了什么核验步骤；
- 哪些情况不能沿用该结论。

审核人无法判断该知识是可复用规则，还是把单个案例答案直接改写了一遍。

### 2. 推荐回复与知识正文重复

截图中的推荐回复基本是在正文前增加“您好”，没有完成“知识正文”和“对外答复”的职责分离。

- 知识正文应服务审核、检索和后续复用，包含判断条件、核验过程、结论和边界。
- 推荐回复应服务一线答疑，使用更自然、简短的表达，但不能丢失关键前提和限制。

### 3. 关联标准项疑似为模型生成的抽象分类

截图中出现类似：

```text
【显示问题】-【闪屏/花屏】
【外观问题】-【屏幕及正面外观】
```

这些文本更像“知识分类路径”或“模型标签”，不能证明它们是标准库中真实存在、具有稳定 ID 和版本的标准项。

当前项目处于无标准案例知识模式。按照项目红线：

- 新候选的 `关联标准项` 必须为空；
- 不主动读取、检索或生成标准关联；
- 已有标准关联值需要原样保留并进入搁置流程；
- 不得把知识分类、关键词或模型猜测写入 `关联标准项`。

截图结果说明需要对**所有生成、导出和同步路径**增加回归检查，避免旧路径或其他出口绕过当前门禁。

### 4. 适用边界容易被放大

例如一条案例只能证明：

```text
某型号、某代际、某条件下，历史答疑采用了某处理方式。
```

如果正文省略型号、代际、测量条件或证据类型，知识会被误读成适用于整个产品品类的通用标准。

## 三、当前项目已经具备的安全基础

以下结论来自当前项目源码，不是对外部插件的推测。

### 1. 无标准模式已经在提示词中禁止生成标准

`src/answer_hub/mimo.py:704-723` 根据 `use_standard_references` 区分两种模式。无标准模式明确要求：

- `standard_refs` 输出空数组；
- 不得根据模型记忆补写标准；
- 不得把质检标准问题伪装成案例知识。

`src/answer_hub/workflow.py:9590-9595` 还会检查模型草稿是否出现标准引用，命中后回退。

### 2. 标准模式采用“允许列表”校验

`src/answer_hub/mimo.py:1715-1722` 校验模型输出的每个 `standard_ref` 是否属于本次检索结果。模型引用未检索到的标准会直接报错。

这种“模型只能从输入候选中选择 ID”的方式值得保留。即使未来重新启用标准模式，也不能让模型自由生成标准名称或分类路径。

### 3. 已有标准关联会保留

`src/answer_hub/workflow.py:8711-8727` 在无标准模式下不会使用模型输出的新标准，而是保留来源记录已有的标准关联。

`src/answer_hub/cz_integration.py:370-371` 会阻止带有已有标准关联的候选直接通过当前无标准入口送审，要求进入标准关联搁置流程。

### 4. 当前提示词已经开始要求具体内容

`src/answer_hub/mimo.py:738-747` 已要求无标准模式正文至少覆盖以下四类信息中的两类：

1. 具体对象、代际或来源问题；
2. 检查项或触发条件；
3. 实际结论或处理方式；
4. 不能适用时的边界。

`src/answer_hub/workflow.py:9600-9631` 发现通用模板后会要求模型重新转写；重写后仍为空泛模板时，会阻止进入内容质量初标。

### 5. 主题来源记录已经可以同步到 CZ

`src/answer_hub/workflow.py:8730-8743` 保存主题来源记录 ID 和工单 ID。

`src/answer_hub/cz_integration.py:634-635` 会把 `主题证据摘要` 作为 `evidence_excerpt` 同步到 CZ。

这提供了主题级追溯基础，但目前还不能追踪“正文中的某一句结论来自哪条记录”。

## 四、当前实现仍然存在的关键缺口

### 1. 转写证据与主题分类证据不一致

`src/answer_hub/workflow.py:8199-8259` 的主题分类证据包已经包含：

- 原子问题；
- 人工校正后的原始核心问题；
- 人工校正后的原始判定结论；
- 历史实际回复；
- 完整会话；
- 阈值与例外；
- 语义摘要。

但真正用于转写的 `_topic_query()` 位于 `src/answer_hub/workflow.py:7694-7715`，仍然主要使用：

- 前五条核心问题；
- 前五条历史实际回复；
- 前五条语义标注依据；
- 第一条记录的意图、对象、现象和解题方式。

它没有把 `原始核心问题` 和 `原始判定结论` 作为独立字段明确放入转写特征。

结果是：人工已经校正的关键背景和结论可能用于“是否值得沉淀”判断，却没有完整进入最终知识写作。

### 2. 仍然使用“前五条”而不是代表性证据

`src/answer_hub/workflow.py:7696-7709` 和 `src/answer_hub/workflow.py:9561-9579` 都存在前五条限制。

简单取前五条会遗漏：

- 不同型号或代际；
- 相反或冲突的判定结论；
- 包含明确阈值的案例；
- 包含例外条件的案例；
- 依赖图片才能判断的案例。

因此模型可能只看到多数案例的直接结论，看不到限制该结论适用范围的少数关键证据。

### 3. 当前输出结构没有“事实引用”

`src/answer_hub/mimo.py:748-765` 的主题转写 JSON 没有以下字段：

- `source_fact_refs`；
- `conflicts`；
- `unsupported_claims`；
- `scope_basis`。

`src/answer_hub/mimo.py:1704-1758` 的结果校验也只检查字段类型、标题格式、置信度和标准允许列表，没有检查正文中的事实是否逐项有来源支持。

当前 `主题证据摘要` 是主题级总摘要，不能证明正文中每个确定结论的来源。

### 4. 通用模板检测属于文本启发式，不等于事实校验

`src/answer_hub/workflow.py:7929-7982` 通过短文本重合和通用表达命中次数判断草稿是否空泛。

这个检查能拦截部分模板，但不能可靠识别：

- 模型用不同措辞编造结论；
- 正文引用了真实对象，但附加了来源中没有的原因；
- 将某型号结论扩大到整个品类；
- 忽略了来源中的冲突或例外；
- 把人工判定结论写成平台通用标准。

### 5. 规则降级仍可能缺少人工判定结论

`src/answer_hub/workflow.py:7731-7736` 的规则草稿主要组合核心问题、语义依据和历史回复。

人工校正后的 `原始判定结论` 没有作为明确字段进入 `_topic_query()`，因此 MiMo 不可用时，规则降级路径仍可能只给出通用核验流程，或遗漏人工已经确认的处理结论。

规则降级结果即使补齐判定结论，也必须继续标记为人工优先审核，不能自动放行。

### 6. 当前初标更关注格式与总体一致性

`src/answer_hub/workflow.py:8899-8999` 的规则初标会检查标题、正文是否为空、标准是否缺失、图片是否需要、正文长度是否过短。

但没有强制检查正文是否包含：

- 适用前提；
- 观察或核验过程；
- 结论依据；
- 适用边界或反例；
- 每个关键结论的来源事实。

因此一段超过 60 字、格式完整但仍然直接给结论的内容，可能通过规则初标。

## 五、建议采用的统一主题转写证据包

建议先把每个主题整理成一个结构化证据包，再交给模型写正文。证据包应与最终知识字段分离。

建议结构：

```json
{
  "topic_id": "TOP-001",
  "product_type": "笔记本",
  "business_line": "自营回收",
  "atomic_questions": [],
  "human_corrected_core_problems": [],
  "human_corrected_judgment_conclusions": [],
  "representative_cases": [
    {
      "source_id": "CASE-001",
      "selection_reason": "典型案例",
      "conversation_excerpt": "",
      "historical_reply": "",
      "observed_condition": "",
      "check_action": "",
      "result": "",
      "boundary_or_exception": "",
      "image_evidence_summary": ""
    }
  ],
  "confirmed_facts": [
    {
      "fact_id": "F001",
      "fact_type": "适用条件",
      "fact": "",
      "source_ids": ["CASE-001"],
      "source_types": ["人工核心问题", "完整会话"],
      "confidence": 0.0
    }
  ],
  "conflicts": [],
  "missing_evidence": [],
  "preserved_standard_references": []
}
```

关键原则：

1. 原子问题和人工核心问题同时保留，不能互相覆盖。
2. 人工判定结论作为独立证据，不埋在摘要中。
3. 每个事实必须有 `fact_id` 和来源记录。
4. 冲突不能静默合并，必须进入 `conflicts`。
5. 已有标准关联只放在 `preserved_standard_references`，不作为本轮生成依据。

## 六、代表性证据选择应替代“前五条”

不建议直接把主题全部案例无差别发送给模型，也不建议继续取前五条。

建议采用确定性的覆盖选择：

1. 选择一条信息最完整的典型案例。
2. 每种不同判定结论至少选择一条。
3. 每种不同型号、代际、平台或适用范围至少选择一条。
4. 有明确数字、阈值或例外条件的记录优先选择。
5. 有证据冲突或人工重点复核标记的记录必须选择。
6. 视觉问题选择一条最有代表性的图片证据摘要；图片本身按需在后续阶段输入。
7. 达到字符预算后停止，但不能因为预算删除唯一的冲突、边界或反例。

每条入选记录必须保存 `selection_reason`，便于审核人理解为什么模型看到了这些案例。

## 七、知识正文不应使用固定文案，但应使用固定语义骨架

优化目标不是所有知识都套同一句模板，而是要求内容具备完整逻辑。

### 1. 具体判定型知识

建议正文至少包含：

```text
适用前提：适用于什么品类、型号、代际、部位或场景。
问题表现：来源案例出现了什么现象或查询结果。
核验方式：需要查看、测量、查询或复测什么。
处理结论：满足哪些条件时采用什么处理方式。
适用边界：哪些型号、证据不足或冲突情况不能沿用。
```

### 2. 流程方法型知识

建议正文至少包含：

```text
使用场景：什么时候使用该流程。
准备条件：需要什么信息、工具或图片。
操作步骤：按顺序完成哪些检查。
结果解释：不同结果分别说明什么。
限制条件：什么情况下不能直接下结论。
```

### 3. 案例解析型知识

如果确实值得沉淀，应明确区分：

```text
案例背景；
可观察事实；
本案例处理；
可复用要点；
不可外推范围。
```

案例的最终结论不能直接被包装成全品类通用规则。

## 八、建议增加来源事实引用

建议模型输出增加：

```json
{
  "source_fact_refs": [
    {
      "claim": "AirPods 一代在当前案例流程中不要求检查查找功能",
      "fact_ids": ["F001", "F003"]
    }
  ],
  "scope_basis": {
    "scope": "耳机-AirPods一代",
    "fact_ids": ["F001"]
  },
  "conflicts": [],
  "unsupported_claims": []
}
```

这些字段不一定展示给最终知识使用者，但必须供 CZ 审核和审计使用。

确定性校验应检查：

1. 所有 `fact_id` 都存在于本次证据包。
2. 确定性结论至少引用一个“完整会话、人工判定结论或历史实际回复”事实。
3. 适用范围不能比来源事实覆盖范围更宽。
4. `conflicts` 非空时必须重点人工复核。
5. `unsupported_claims` 非空时禁止标记通过。
6. 正文中的数字、阈值、型号和代际必须能在引用事实中找到。

## 九、关联标准项的正确处理

### 当前无标准模式

新候选必须满足：

```text
关联标准项 = 空
```

不得写入：

- 知识分类；
- 一级/二级分类路径；
- 模型猜测的标准名称；
- 从正文自动抽出的标签；
- 类似 `【显示问题】-【闪屏/花屏】` 的抽象路径。

### 已有标准关联

来源数据已经有值时：

1. 原样保留；
2. 标记为“已有标准关联”；
3. 进入标准关联搁置；
4. 不允许本轮模型修改、补充或覆盖；
5. 不通过当前无标准入口直接送审。

### 未来重新启用标准模式

只能采用“检索候选允许列表”：

1. 程序从真实标准库检索带稳定 ID、版本和状态的候选项。
2. 模型只能选择候选 ID，不能自由生成名称。
3. 输出 ID 必须经过确定性允许列表校验。
4. 标准失效、版本冲突、分数低或前两名差距小时进入人工审核。

当前项目的 `mimo.py` 和 `atomic_standard_mapper.py` 已有这种允许列表、阈值和人工复核思想，但当前生产无标准模式不得主动启用标准检索。

## 十、建议的两阶段转写与三层校验

### 阶段一：事实抽取

模型只负责从代表性案例中抽取：

- 背景；
- 对象；
- 条件；
- 检查动作；
- 观察结果；
- 人工结论；
- 边界；
- 冲突；
- 来源 ID。

这一阶段不生成可发布正文。

### 阶段二：知识写作

模型只能使用阶段一确认的事实，按知识形态生成：

- 主标题；
- 副标题；
- 知识正文；
- 推荐回复；
- 适用范围；
- 关键词；
- 来源事实引用。

### 三层校验

1. **结构校验**：字段、枚举、长度、JSON 和引用 ID 合法。
2. **事实校验**：结论、型号、阈值、范围均有来源支持；冲突未被隐藏。
3. **业务门禁**：无标准模式不生成标准关联；低置信度、规则降级、图片不足和冲突候选进入人工审核；不得自动发布。

## 十一、建议补充的测试

建议后续代码修改至少增加以下测试：

1. 人工核心问题和人工判定结论明确进入转写证据包。
2. 规则降级路径能使用人工判定结论，但强制人工优先审核。
3. 主题超过五条时，代表性选择能保留唯一的边界案例。
4. 主题超过五条时，代表性选择能保留相反结论和冲突案例。
5. 模型输出的每个 `source_fact_ref` 必须属于证据包。
6. 确定性结论没有事实引用时，初标不得通过。
7. 正文只写个案最终结果、没有前提和边界时，触发重写或转人工。
8. 适用范围大于来源事实范围时，触发重点复核。
9. 无标准模式下模型输出抽象分类路径作为标准项时，结果被清空或拦截。
10. 已有标准关联保持原值并进入搁置，不被模型覆盖。
11. 推荐回复不能只是知识正文加“您好”，必须保留关键前提且更适合一线发送。
12. CZ 同步中保留主题来源记录和事实引用，但最终状态仍为待审核。

## 十二、实施优先级建议

### P0：先解决错误标准关联

- 对全部转写、导出、CZ 同步入口增加无标准模式门禁。
- 新候选 `关联标准项` 强制为空。

## 十三、与项目业务红线的兼容判断

| 方法 | 判断 | 说明 |
| --- | --- | --- |
| 结构化事实抽取 | 可采用 | 不引入外部事实，只整理现有证据 |
| 代表性证据选择 | 可采用 | 替代前五条截断，保留边界与冲突 |
| 来源事实引用 | 可采用 | 提升审计和 CZ 人工复核能力 |
| 固定语义骨架 | 可采用 | 固定结构，不固定文案 |
| 独立内容校验 | 可采用 | 不修改沉淀价值，只审查内容质量 |
| 标准 ID 允许列表 | 仅未来标准模式采用 | 当前无标准模式不得主动检索 |
| 自动生成标准名称或路径 | 不可采用 | 会产生截图中的抽象、虚假关联 |
| 覆盖已有标准关联 | 不可采用 | 必须原样保留并搁置 |
| 根据个案自动发布知识 | 不可采用 | 只能进入 CZ 待审核 |
| 跳过 Qwen3 和 CZ 终审 | 不可采用 | 违反现有业务红线 |

## 十五、最终判断

截图中的问题不能只靠“把提示词写得更详细”解决。需要同时改造：

```text
证据选择
→ 结构化事实包
→ 按知识形态转写
→ 事实来源引用
→ 确定性校验
→ CZ 人工复核
```

最优先解决的是：

1. 新候选不再生成抽象关联标准项；
2. 人工核心问题和判定结论完整进入转写；
3. 不再取前五条，而是选择典型、边界、冲突和例外证据；
4. 正文必须包含前提、核验过程、结论和边界；
5. 每个关键结论可以追溯到具体来源记录；
6. 规则降级、冲突和证据不足结果继续人工优先审核；
7. 所有结果只进入 CZ 待审核，不自动发布。
