## 一、切换记录（生产切到本机）

### 1.1 做了什么

**改动范围只有两行配置** —— 服务器 `/opt/knowledge-kb/.env` 的第 **88** 行与第 **93** 行，端口由 `:8780` 改为 `:18780`：

| 行号 | 变量名 | 改动 |
|---|---|---|
| 88 | `ANSWER_HUB_BASE_URL` | `...:8780` → **`...:18780`** |
| 93 | `ANSWER_HUB_API_BASE_URL` | `...:8780` → **`...:18780`** |

> ⚠️ **本文不抄录这两行的完整取值**（仓库是公开仓库，`.env` 里的值一律不进仓库）。只记录**行号、变量名、端口变化**这三件事。

**服务器 nginx 未做任何动作** —— 不 `reload`、不 `restart`。宿主机宝塔 nginx 反代多站点，且本次没有新增/修改站点配置的需求。

### 1.2 怎么重建容器的（关键）

重建 `kb-backend` 用的是「**打钉镜像文件 + `--no-build`**」：

- 「打钉」= 额外挂一份 compose 覆盖文件，把 `kb-backend` 的**镜像名写死**；
- `--no-build` = **明确禁止现场重新构建镜像**。

> ⚠️ **为什么必须这样做**：不钉镜像 + 不带 `--no-build` 的 `docker compose up` 有可能**顺带把当前代码重新构建一遍**，那就会把「一次单纯的配置切换」变成「一次夹带代码变更的部署」—— 万一出问题，无法判断是配置的锅还是代码的锅。本次切换**只要换配置，不要换代码**。

## 三、回滚能力（已演练，2026-09-30 16:07）

### 3.1 演练做了什么

演练脚本：[`../scripts/local-migration/rollback-drill.sh`](../scripts/local-migration/rollback-drill.sh)。核心动作是**双向切换各做一遍**：

1. **回退方向**：改 `.env` 第 88/93 行回 `:8780` + 用**与切换时相同的方式**（钉镜像文件 + `--no-build`）重建 `kb-backend`；
2. **前滚方向**：再改回 `:18780` + 同样方式重建，回到本机生产。

### 3.2 实测结果

| 方向 | 结果 |
|---|---|
| 回退 → `:8780` | `/ready` **6 秒**恢复；容器内 `ANSWER_HUB_API_BASE_URL` 实测 = `http://172.18.0.1:8780` ✅ |
| 前滚 → `:18780` | `/ready` **4 秒**恢复；容器内指向实测 = `:18780` ✅ |
| 两次重建的镜像 | 名称与 ID **均未变**（仍是 `knowledge-kb-backend:master-2e1d1f00-20260930` / `sha256:20d751b8...`） → **演练也没夹带代码** |
| 演练后状态 | ✅ 已复原（`.env` 指 `:18780`、旧服务停回 `inactive`） |

> ✅ 结论：**改 `.env` + 重建容器这条路，两个方向都实测走得通**，且耗时是**秒级**（4~6 秒恢复 `/ready`），比运行手册原先「502 窗口可能数分钟」的估计更乐观。

### 3.3 ⚠️ 一个必须写清的重要纠正

**单独执行 `systemctl start answer-hub-api`【不等于】回滚。**

原因：回滚的**实质**是把 `kb-backend` 的数据源换回去，而这是由 **`.env` 的 88/93 行 + 重建容器**决定的。切换后 `.env` 指向的是 `:18780`（隧道 → 本机）。此时哪怕你把服务器旧服务启动起来，`kb-backend` **依然在打 `:18780`**，根本不会用到它。

所以：

| 动作 | 实际效果 | 是不是回滚 |
|---|---|---|
| `systemctl start answer-hub-api` | 旧服务重新监听 `:8780`，**但生产流量仍走 `:18780` → 本机** | ❌ **不是回滚**，只是**让退路重新待命** |
| 改 `.env` 88/93 行回 `:8780` + 重建 `kb-backend` | 生产流量真正切回旧服务 | ✅ **这才是回滚** |

**正确理解**：恢复旧服务这件事分两步 —— ①`systemctl start` 把退路「热」起来（因为只 `stop` 未 `disable`，所以这一条随时可做）；②改 `.env` + 重建容器，才是真正把流量搬回去。**只做第 ① 步而以为已经回滚，是本次迁移中最容易踩的认知陷阱。**

## 四、四项计划任务改为 S4U（2026-09-30 15:48）

### 4.1 为什么要改

本机四项守护任务原先的 `LogonType` 是 **`Interactive`**，它的含义是「**必须有一个交互式登录会话**这个任务才会跑」。

**风险场景**：只要有人对 `Administrator` 账户执行【注销】，交互式会话消失 → **四项任务全部停止** → 本机 API、隧道、观察、嵌入守护**同时全停**。

⚠️ **这个风险在 15:51 停用旧服务之后会被放大到最严重**：旧服务已停，**本机是唯一的生产路径**。此时如果四项任务因注销而全停，**生产就彻底没有 Answer Hub**，且没有任何自动接管方。

**`S4U`**（Service For User）的含义是「以该用户身份运行，但**不依赖交互式登录会话**」，因此不受注销影响。

### 4.2 改动对照

| 任务名 | 改前 `LogonType` | 改后 `LogonType` |
|---|---|---|
| `AnswerHub-API-Local` | `Interactive` | **`S4U`** |
| `AnswerHub-Tunnel` | `Interactive` | **`S4U`** |
| `AnswerHub-Watch` | `Interactive` | **`S4U`** |
| `Docker-Embedding-Watchdog` | `Interactive` | **`S4U`** |

时间：**2026-09-30 15:48**。

## 五、监控判据（**最容易看错的一节**）

`observation.log` 由 `AnswerHub-Watch` 任务**每 10 分钟写一行**。字段含义如下：

| 字段 | 探的是谁 | 判断生产时算不算数 |
|---|---|---|
| `local=` | **本机** Answer Hub（本机 `:8780`） | 辅助（本机端点本身是否活着） |
| `rollback=` | **服务器本地旧服务**（服务器 `127.0.0.1:8780`） | ❌ **不算数** |
| `tunnel=` | 隧道 `:18780`（新生产路径入口） | ✅ **算数** |
| `e2e=` | 从 `kb-backend` **容器内部**真实调用本机业务接口 | ✅ **算数** |

### ⚠️ 判断生产只看 `tunnel=` 与 `e2e=`

**`rollback=` 在停用之后预期恒为 `000`，这不是故障。**

旧服务已经按计划停掉了，服务器本地 `:8780` 当然不通。如果你把 `rollback=000` 当成「生产挂了」，就会得到**永久误报** —— 监控软件天天喊生产故障，而生产其实完全正常。这是最难排查的一类误判：**报警的不是生产，而是一条已经不该被使用的退路。**

> ⚠️ **这个误判真实发生过**：停用当天 `_smoke.ps1` 就因此固定报 `FAIL=2`。已于 2026-09-30 修正（模拟测试与观察日志按「旧服务已停用」的新判据判定，`rollback=000` / 退路 `inactive` 归为 `PASS`）。修正详情见停用方案 4.1。

## 六、已知风险（如实列出）

### 风险 1：服务器一旦重启，旧服务会自动回来占住 `:8780`

**原因**：停用时**只 `stop`、未 `disable`**，`is-enabled` 仍是 **`enabled`**。所以服务器重启后，systemd 会自动把旧服务拉回 `active` 并监听 `:8780`。

**后果**：生产本身**不受影响**（`kb-backend` 打的是 `:18780` 隧道 → 本机）；但冒烟测试的【G2】回滚退路检查会报 **WARN**，提示「旧服务意外回到了 `active`，需人工确认」。

**为什么不 `disable`**：`enabled` 是本次刻意保留的**退路** —— 需要回滚时 `systemctl start` 或重启即可拉起，不必改单元配置。

### 风险 2：本机重启后能否自愈 —— **从未实证**

**现状**：本机重启后四项任务是否会自动拉起、生产是否会自动恢复，**至今没有真实验证过一次**（无法在不停机的前提下产生一次真实重启）。停用方案第 1.3 节第 7 条、运行手册第八节第 6 条都记着这条。

**已做的补救**：注册了计划任务 **`AnswerHub-Boot-Verify`**（触发器 = **Boot** 开机触发，`LogonType` = **S4U**）。每次开机后，它自动把**开机后 5 分钟内**的状态写入：

```
E:\answer-hub-runtime\boot-verification.log
```

记录内容（每 30 秒一轮，共 10 轮）：开机时间、四项任务各自的 `State`/`LogonType`、本机 API、隧道 `18780`、公网、本机嵌入容器。

> ⚠️ **这个日志只能「记录」，不能「代替验证」**：它到目前为止**尚未捕获到一次真实开机**（没有发生过重启）。所以「本机重启后能否自愈」仍然是**未验证状态**，不是「已验证可用」。
