# 模型网关代理本机运行手册（第三条隧道链路）

> 状态：已上线并实测通过。本手册记录背景、架构、运维步骤、验证方法与已知风险。
> 相关脚本：`prototypes/answer-hub/scripts/local-migration/model-gateway-*.ps1|py`、`backend-model-gateway.yml`

## 一、这是什么问题

「工作台 → 置信度训练」页面会弹出：

> 内部 DeepSeek flash API 尚未配置；请配置 DEEPSEEK_*，或提供已有的 GROUP_LLM_API_KEY。

触发点是页面调用 `POST /api/v1/confidence-training/model-connection-test`，它最终走到
`backend/app/services/model_annotation.py` 的 `_call_deepseek_flash()`。

实测到的三层原因（缺一个都修不好）：

| # | 事实 | 实测证据 |
|---|---|---|
| 1 | `kb-backend` 容器里没有任何 `DEEPSEEK_*` / `GROUP_LLM_*` 变量 | `docker exec kb-backend printenv` 无匹配 |
| 2 | 服务器 `.env` 里也没有这些变量 | `grep '^DEEPSEEK' /opt/knowledge-kb/.env` 无匹配 |
| 3 | **服务器根本连不上模型网关** | DNS 解析到 `10.47.195.10`，但 `TCP 443` 连接失败 |

第 3 条是关键：**只在服务器补 key 是没用的**，报错只会从 `CONFIG_MISSING`
变成网络超时 / `NETWORK_ERROR`。本机（开发机，公司内网）到同一个地址：443 是通的。

## 二、目标架构（与已有两条链路同构）

```
┌──────────── 服务器 ─────────────┐         ┌──────────── 本机开发机 ────────────┐
│ kb-backend 容器                  │         │ model-gateway-proxy.py             │
│  DEEPSEEK_BASE_URL=              │  SSH    │  监听 0.0.0.0:19000                │
│   http://host.docker.internal    │ 反向隧道 │  用 HTTPS 连真实网关：             │
│          :19000/v1  ─────────────┼────────▶│  https://tokenhub.zhuanspirit.com  │
│                                  │ :19000  │        /codex/v1/chat/completions  │
│ 回答/嵌入等其余链路不动            │         │  真实 key 只在这里，从不外发        │
└──────────────────────────────────┘         └────────────────────────────────────┘
```

本机现有三条「本机跑服务 + 服务器穿 SSH 反向隧道调用」的链路：

| 链路 | 服务器端口 | 本机端口 | 说明 |
|---|---|---|---|
| Answer Hub | `:18780` | `8780` | 生产路径，**不要动** |
| GPU 嵌入 | `:18080` | `8080` | 生产路径 |
| **模型网关代理** | **`:19000`** | **`19000`** | 本手册 |

## 三、文件与计划任务

本机脚本（`E:\answer-hub-runtime\`，仓库内为脱敏镜像）：

| 文件 | 作用 |
|---|---|
| `model-gateway-proxy.py` | 纯标准库 HTTP 代理，`/v1/*` → 真实网关；`/health` 供探活 |
| `model-gateway-watchdog.ps1` | 自愈守护：每分钟探活，坏了就按 PID 精确重启 |
| `model-gateway-tasks.ps1` | 注册计划任务（幂等，可重复执行） |
| `backend-model-gateway.yml` | 服务器侧 compose overlay（`E:\answer-hub-runtime\` 内的那份会被推到服务器 `/opt/knowledge-kb-runtime/`） |

两个计划任务（与 `AnswerHub-Tunnel` 完全同一套参数）：

| 任务名 | 动作 |
|---|---|
| `ModelGateway-Proxy` | 每分钟跑一次 `model-gateway-watchdog.ps1`（Boot 触发器 + 1 分钟重复） |
| `ModelGateway-Tunnel` | 常驻 SSH 反向隧道 `-R 0.0.0.0:19000:<本机IP>:19000` |

共同参数：`MultipleInstances=IgnoreNew`、`ExecutionTimeLimit=PT0S`、
`LogonType=S4U`、`RunLevel=Highest`、`StartWhenAvailable=true`。

> `LogonType=S4U` 很关键：任务不依赖用户登录，且**继承用户环境变量**，所以代理能在
> 不把任何密钥写进文件的前提下读到它们（已实测：任务上下文里
> `GROUP_LLM_API_KEY` 长度正常，注册表 `HKCU\Environment` 也可读作兜底）。

## 四、密钥放在哪（设计选择）

代码里 `if not base_url or not api_key: raise CONFIG_MISSING`，所以**服务器侧
`DEEPSEEK_API_KEY` 不能为空**。两种选法：

| 方案 | 说明 | 结论 |
|---|---|---|
| A：真实网关 key 放服务器 `.env` | 简单，但真实 key 落到服务器明文 `.env`，且明文经过 SSH 隧道下发 | ❌ 不采用 |
| B：真实 key 只留在本机代理，服务器只放一把**隧道访问令牌** | 泄露影响面小；服务器即使被读也只能读到一条隧道口令，无法直接调用公司网关 | ✅ 采用 |

采用的方案 B 细节：

- 真实网关 key：本机用户环境变量 `GROUP_LLM_API_KEY`，运行时读，不落盘、不打印。
- 隧道访问令牌：本机新建用户环境变量 `MODEL_GATEWAY_CLIENT_TOKEN`（随机 48 位十六进制）。
  服务器 `.env` 的 `DEEPSEEK_API_KEY` 就是这把令牌；代理校验通过后**由代理自己替换**成真实 key。
- 另有一把管理员令牌 `MODEL_GATEWAY_ACCESS_TOKEN`，只用于人工探活。
- 代理只接受这两个令牌之一（常量时间比较），其他一律 `401`，
  避免 `:19000` 被当免费网关白用。

> 如果 `.env` 泄漏最坏情况：攻击者只能通过隧道调用模型，无法拿到真实 key；
> 吊销方式是把本机的 `MODEL_GATEWAY_CLIENT_TOKEN` 换掉并重建容器。

## 五、部署步骤（相当于从零重做）

### 1. 本机：装令牌（只做一次，值不要贴进任何文档或提交）

```powershell
$bytes = New-Object byte[] 24
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes)
$tok = -join ($bytes | ForEach-Object { $_.ToString('x2') })
[Environment]::SetEnvironmentVariable('MODEL_GATEWAY_CLIENT_TOKEN', $tok, 'User')   # 服务器会说这把
$bytes2 = New-Object byte[] 24
[System.Security.Cryptography.RandomNumberGenerator]::Create().GetBytes($bytes2)
$tok2 = -join ($bytes2 | ForEach-Object { $_.ToString('x2') })
[Environment]::SetEnvironmentVariable('MODEL_GATEWAY_ACCESS_TOKEN', $tok2, 'User')  # 人工探活用
```

`GROUP_LLM_API_KEY` 已存在于用户环境变量，无需新建。

### 2. 本机：注册计划任务

```powershell
$env:MODEL_GATEWAY_SSH_TARGET = 'root@<SERVER_HOST>'
$env:MODEL_GATEWAY_LOCAL_IP   = '<LOCAL_TAILSCALE_IP>'
E:\PowerShell\pwsh.exe -NoProfile -ExecutionPolicy Bypass -File E:\answer-hub-runtime\model-gateway-tasks.ps1
Start-ScheduledTask -TaskName 'ModelGateway-Proxy'
```

脚本可以重复执行（幂等）。脚本对 `-Trigger` 的重复模式不兼容时会改用显式任务
XML 注册，这是刻意的：现有 `AnswerHub-Tunnel` 就是用这个重复模式在跑。

### 3. 服务器：加变量 + 装 overlay（不要改 `docker-compose.yml`）

原因：base compose 用**显式 `environment:` 白名单**注入容器变量，
只往 `.env` 里加 `DEEPSEEK_*` 是**进不去容器**的；改 base compose 又会让它和
仓库版本进一步分叉。所以用一个新的 overlay。

```bash
# 备份（务必先做）
cp -a /opt/knowledge-kb/.env /opt/knowledge-kb-runtime/deepseek-gateway-<时间戳>/.env.bak

cat >> /opt/knowledge-kb/.env <<'EOF'

# --- DeepSeek-flash gateway via local proxy + SSH reverse tunnel ---
DEEPSEEK_BASE_URL=http://host.docker.internal:19000/v1
DEEPSEEK_API_KEY=<本机 MODEL_GATEWAY_CLIENT_TOKEN 的值>
DEEPSEEK_MODEL=deepseek-flash
EOF
chmod 600 /opt/knowledge-kb/.env
```

`DEEPSEEK_BASE_URL` **必须用 `host.docker.internal`，不能用 `127.0.0.1`**：
容器里的 `127.0.0.1` 是容器自己，不是宿主机。

把 `backend-model-gateway.yml` 放到 `/opt/knowledge-kb-runtime/`，然后重建：

```bash
cd /opt/knowledge-kb
docker compose \
  -f /opt/knowledge-kb/docker-compose.yml \
  -f /opt/knowledge-kb/docker-compose.embedding-cpu.yml \
  -f /opt/knowledge-kb-runtime/docker-compose.host-pg.yml \
  -f /opt/knowledge-kb-runtime/docker-compose.server.yml \
  -f /opt/knowledge-kb/.codex-deploy-20260929-pre-release/compose.release.yml \
  -f /opt/knowledge-kb/.codex-deploy-20260929-correct-frontend/compose.frontend.json \
  -f /opt/knowledge-kb/.codex-deploy-20260930-master-f851/compose.master.yml \
  -f /opt/knowledge-kb/.codex-deploy-20260930-layout-7bc/compose.layout.yml \
  -f /opt/knowledge-kb/.codex-deploy-20260930-embedded-chat-2e1/compose.embedded-chat.yml \
  -f /opt/knowledge-kb-runtime/compose.pin-image.yml \
  -f /opt/knowledge-kb-runtime/.codex-build-overview-filter-7ee769/compose.overview-filter.yml \
  -f /opt/knowledge-kb/.codex-deploy-20260930-people-count-18/compose.people.yml \
  -f /opt/knowledge-kb-runtime/backend-model-gateway.yml \
  --env-file /opt/knowledge-kb/.env up -d --force-recreate --no-deps --no-build backend
```

> ⚠️ 上面这一串是本项目**实际在用的** `config_files`（取自运行中容器的
> `com.docker.compose.project.config_files` 标签）。它与「钉镜像 rebuild 命令」
> 的差别是**多了** `compose.overview-filter.yml`、`compose.people.yml`，
> **少了** `backend-host-gateway.yml`（后者只加 `host.docker.internal` 和 uploads 挂载，
> 而 `extra_hosts` 已由 base compose 提供）。用错组合会静默回退掉人名看板等改动。
> 改动前务必先用 `docker inspect kb-backend --format '{{index .Config.Labels "com.docker.compose.project.config_files"}}'` 核对一次。

`--no-build` + `compose.pin-image.yml` 保证不会重建镜像；中断时间实测约 4~6 秒。

## 六、验证清单

```bash
# 1) 服务器侧看隧道是否活着
python3 -c "import urllib.request as u; print(u.urlopen('http://127.0.0.1:19000/health', timeout=8).status)"

# 2) 容器里变量进去没有（只看名字）
docker exec kb-backend printenv | grep -E '^DEEPSEEK' | cut -d= -f1

# 3) 容器 → 网关真实调用
docker exec kb-backend python -c "
import json,os,urllib.request
r=urllib.request.urlopen(urllib.request.Request(
  os.environ['DEEPSEEK_BASE_URL'].rstrip('/')+'/chat/completions',
  data=json.dumps({'model':os.environ['DEEPSEEK_MODEL'],
    'messages':[{'role':'user','content':'Reply {\"ok\": true} json only'}]}).encode(),
  headers={'Authorization':'Bearer '+os.environ['DEEPSEEK_API_KEY'],
           'Content-Type':'application/json'}), timeout=60)
print(r.status, json.loads(r.read())['model'])"

# 4) 生产就绪 + 公网
curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1:8000/ready
curl -s -o /dev/null -w '%{http_code}\n' https://<PUBLIC_DOMAIN>/app

# 5) 镜像未变
docker inspect kb-backend --format '{{.Config.Image}} {{.Image}}'
```

页面弹窗是否消失，最终以 `POST /api/v1/confidence-training/model-connection-test`
返回 `{"status":"connected", ...}` 为准（需要登录态）。

## 八、已知风险与不确定项

1. **本机是单点**。开发机关机 / 睡眠 / 断网 / 退内网时，这条链路和 Answer Hub 链路
   会同时失效。此时置信度训练页面的报错会从 `CONFIG_MISSING` 变成
   `TIMEOUT` / `NETWORK_ERROR` —— **这是行为变化，需要知悉**：以前是「没配置」，
   现在是「配置了但连不上」。
2. **`:19000` 由服务器 `0.0.0.0` 监听**（与 `:18780` / `:18080` 一致）。
   目前靠代理自带的访问令牌挡住滥用；如果安全要求更高，应改为只绑定 Tailscale 地址。
3. **网关侧限流/配额未评估**。`response_format=json_object` 实测可用，
   但并发上限、QPS 限制都没有测过。
4. **本机属于「新电脑」，但已在承载服务器生产**。这条链路把它变成了第四个
   生产依赖，建议纳入现有的巡检脚本。
5. **任务 XML 里的重复模式**（`Interval PT1M` / `Duration P3650D`）是通过显式 XML
   注册的，因为 `Register-ScheduledTask -Trigger` 会拒绝同样的值。改动时不要
   试图改回 cmdlet 写法。
6. **`.env` 里的 `DEEPSEEK_API_KEY` 是隧道令牌，不是模型密钥**。后人若误以为是
   真实 key 并直接拿去调 `tokenhub`，会得到 401 —— 这是预期行为，不是故障。
