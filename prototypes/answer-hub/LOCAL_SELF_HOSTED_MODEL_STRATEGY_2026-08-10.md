# 答疑中台知识库：本地/自托管模型降本策略

查询日期：2026-08-10
范围：中文会话、图片/视频证据、主题聚类、主题分类、知识转写与审核。本文只读取项目说明和厂商/框架官方资料；未读取 `.env`、真实数据或 `outputs/`，未调用真实 API，未改动程序或配置。

## 先给结论

**可以逐步用本地模型降低 API 支出，但现在不应该马上“训练一个模型全面替代 API”。**

最实际的路线是：

1. 保留现有确定性规则、人工审核、Qwen3 查重和 CZ 终审；这些不应交给任何模型决定。
2. 先用一台本地 GPU 部署 `Qwen2.5-VL-3B-Instruct` 做图文/视频理解的影子测试；质量通过后，优先承接重复且结构化的视觉事实提取和纯文本短任务。
3. 低置信、图片/视频不清晰、长视频、多证据冲突、跨记录聚类裁决仍调用 API 或转人工复核。
4. 先积累并验收人工真值，再训练轻量分类器；LoRA 是后续实验，不是当前节流的前置条件。

这样不会关闭第二部分必需的图片/视频信息提取，而是把“每条都付费的视觉调用”逐步变成“本地优先、风险 API 兜底”。

## 当前项目决定了哪些边界

项目当前主链路以 MiMo 的 `direct_mimo` 完成会话语义标注、原子问题和 1～N 聚类；完整流程仍会读取媒体策略。项目已有本地 Qwen3 Embedding，用于 CZ 的重复拦截，但它是文本向量模型，并不能分析图片或视频。[AI_HANDOFF_LATEST.md](AI_HANDOFF_LATEST.md) [README.md](README.md)

以下内容**必须一直保持本地代码/人工控制，不能用“训练模型”绕过**：

- 回收业务层级和产品类型硬边界；字段与聊天冲突时进入人工复核。
- 无标准案例模式：不读取、检索或生成标准关联；新候选的关联标准项保持为空，已有值不得覆盖。
- 低置信、模型降级、证据冲突、图片依赖无法验证的候选进入人工审核。
- Qwen3 重复检测、CZ 待审核、人工终审和人工发布；系统不得自动发布知识。

### 现有本地主题标签模型不能用于自动放行

仓库中现有的 `topic-label-hash-nb-v1` 只是实验基线：**人工真值为 0 条**，训练来源是筛选后的 MiMo 伪标签，且特意混入了部分上游风险样本。项目说明已明确它 `production_eligible=false`，所有结果强制人工复核，不得接入生产自动审核、送审或发布。

因此，不能把它当作“已经训练好的替代模型”。用模型自己的伪标签继续训练，最多是在复制原模型的判断，也可能放大其错误；这是一项基于项目现状作出的风险判断，而不是可用的生产验收结果。[AI_HANDOFF_LATEST.md](AI_HANDOFF_LATEST.md) [README.md](README.md)

## 推荐的本地/API 分工

| 环节 | 首选方案 | 为什么 |
|---|---|---|
| 清洗、字段校验、产品/业务层级隔离、证据追踪、JSON 校验、缓存、路由 | 现有本地规则 | 可解释、几乎没有 Token 成本，而且是业务红线。 |
| 候选召回、文本相似度、最终重复拦截 | 现有本地 Qwen3 Embedding + 阈值/规则 | 项目已有本地部署基础；它只作相似度证据，不替代人工或硬边界。 |
| 主题问题分类、是否值得沉淀 | 人工真值重训后的轻量本地分类器，先只做“人工复核辅助” | 标签空间小、结构化，最适合先本地化；但现有模型没有人工真值，当前不能放行。 |
| 常见、清晰的图片/短视频事实提取 | 本地 `Qwen2.5-VL-3B-Instruct` 影子测试后承接 | Qwen 官方模型卡提供图像/视频输入，并允许用图片像素预算和视频 FPS 控制视觉 Token；它也是 Qwen 官方微调示例覆盖的起点。[Q1][Q3] |
| 多图/长视频、画质差、需精细判定、媒体与人工字段冲突 | API 或人工复核 | 这些是本地小模型最容易误判的高风险路径；不能为了省钱静默降为纯文本。 |
| 跨记录 1～N 主题聚类、知识转写、内容质量初标 | 本地模型先影子对照；质量不达标继续 API | 这些步骤影响合并、拆分和知识内容，必须以脱敏样本验收，而非凭模型参数量判断。 |

本地视觉模型可通过 vLLM 暴露 OpenAI 兼容服务，便于后续在不改变业务审核语义的前提下增加“本地优先 / API 兜底”路由。vLLM 官方也列出多模态输入与 OpenAI 兼容服务器能力；具体 Qwen3-VL 支持版本要与部署时的 vLLM 版本一并锁定验证。[V1][V2]

## 硬件与部署：先按已有设备决定，不建议先买大服务器

下面是**项目规划估算，不是厂商保证的最低配置**。实际显存会随模型版本、量化方法、图片分辨率、视频帧数、上下文长度和并发数显著变化；上线前必须用脱敏样本压测 OOM、延迟和视觉准确率。

| 现有设备 | 建议用途 | 结论 |
|---|---|---|
| 没有 NVIDIA GPU，或仅 CPU | 保留 Qwen3 Embedding、规则和人工审核；视觉仍用低价 API | 不建议在 CPU 上跑视频视觉模型，速度通常无法支撑批量流程。 |
| NVIDIA 12–16GB 显存 | `Qwen2.5-VL-3B-Instruct` 的低并发 POC；限制图片像素和视频 FPS/帧数 | 可验证能否吃掉常见视觉任务，难例继续 API。 |
| NVIDIA 24GB 显存 | 优先本地 3B 的较高质量配置，或试验更大模型的量化推理；低并发运行 | 是较稳妥的内部试点档位，仍要为视频和 KV 缓存预留空间。 |
| NVIDIA 48GB 及以上 | 8B 更高精度/更高并发，或开展小模型 LoRA 实验 | 只在影子测试证实质量和调用量足够时才值得投入。 |

推荐把模型放在独立的 Linux GPU 主机/虚拟机或 Docker GPU 环境中，Answer Hub 仅经内网调用。vLLM 官方安装和硬件支持说明以 Linux + CUDA/NVIDIA 路线最成熟；服务应只暴露给受控内网并配合鉴权/网关，不能把无保护的推理端口公开到互联网。[V3][V2]

`Qwen2.5-VL-3B-Instruct` 适合作为第一轮固定基线：它同时支持图像和视频，并可以设置图片像素预算、视频 FPS 来控制视觉 Token。若本机显存较紧，可另测 `Qwen3-VL-2B-Instruct` 作为**只推理**的轻量候选；不要把不同版本、不同参数规模混在同一次评估中，否则成本、输出和质量无法归因。[Q1][Q2]

## 训练与 LoRA：正确顺序

### 现在可做：训练轻量分类器，不训练“万能视觉大模型”

先由人工在现有审核工作簿中标注主题问题分类、是否值得沉淀、是否进入训练集，并保留产品品类、业务层级、边界样本和人工复核原因。训练/验证必须按产品类型和主题拆分，避免同一主题或近似记录同时出现在训练集与测试集。

首个目标应只是“给审核员建议标签 + 置信度 + 进入人工队列的原因”，不是自动创建知识。验收指标至少包括：每品类准确率、错误合并率、错误拆分率、人工修改率、低置信召回率，以及对风险样本的误放行数。

### 后续才评估 LoRA

LoRA/PEFT 的价值是只训练少量适配参数，而不是从零训练整个基础模型；官方 PEFT 文档将其定位为更省显存、可在消费级硬件上微调大模型的方式。[P1]

对视觉训练更应保守：Qwen 官方 `qwen-vl-finetune` 已给出 Qwen2.5-VL-3B 的 LoRA 配置和视频样本控制示例，但示例使用 BF16、面向 Ampere 及以上 GPU，并没有承诺 3B/7B 视频 LoRA 的最低显存；其 32B LoRA 示例需要 8 张 80GB H100。故不能承诺“某张显卡一定能训成”，只能先固定图片尺寸、视频帧数和上下文后压测。[Q3]

但对本项目而言，LoRA 只有同时满足下面条件才值得启动：

1. 已有足够、持续沉淀的**人工真值**，覆盖 12 个品类、常见与边界场景、图片和视频依赖样本；
2. 有冻结的脱敏测试集，且不与训练集重叠；
3. 明确训练目标，例如“视觉事实结构化提取”或“主题分类”，而不是把聚类、转写、审核和发布混成一个目标；
4. 能与未微调的本地基线和当前 API 基线对照，并保存模型/数据/提示词版本、混淆矩阵和回退规则；
5. 无论结果如何，仍保留人工审核、Qwen3 查重和 CZ 终审。

在这些条件前，不建议把有限预算花在 GPU 租赁和 LoRA 训练上。对于目前的 0 条人工真值状态，先标注数据通常比先训模型更能减少后续返工。

## 建议的三阶段试点（不改变现有生产红线）

### 阶段 A：先建立成本和质量基线

1. 从现有运行汇总中只读取聚合指标：调用次数、重试次数、输入/输出 Token、各阶段成本和媒体任务比例；不复制真实会话到报告。
2. 固定脱敏评测集：现有 60 对聚类标注样本之外，补齐代表性图片/短视频、模糊媒体、字段冲突和跨品类边界样本。
3. 先设定“本地模型可以接管”的通过门槛；未达到则继续 API，不做静默替换。

### 阶段 B：3B 本地视觉模型影子运行

1. 在独立 GPU 环境部署固定版本的 `Qwen2.5-VL-3B-Instruct` 与固定 vLLM 版本，并固定图片像素预算、视频 FPS 和最大帧数。
2. 同一份脱敏请求同时保留当前基线与本地结果，仅比较，不写回正式候选、不调用自动送审。
3. 比较视觉事实准确率、JSON 成功率、延迟、显存峰值、单条失败率、API 回退率和人工修改率。
4. 只有常见且高一致性的任务才能变为“本地优先”；低置信或错误风险仍转 API/人工。

### 阶段 C：从审核反馈训练轻量模型

1. 用审核完成后的人工标签训练/重训主题分类与沉淀价值模型。
2. 先把它作为审核页建议，不作为自动放行依据。
3. 只有在按品类验收稳定、误放行可控且项目生产门禁仍生效时，才讨论小范围自动化；仍只能写入 CZ 待审核，绝不自动发布。

## 这条路线什么时候比 API 便宜

本地模型消灭的是“每次请求的 Token 费用”，但会引入一次性 GPU、维护、电力、故障处理、模型升级和人工验收成本。因此：

- **已有可用 16GB/24GB NVIDIA GPU，且视觉调用量持续较高**：先做 3B POC，成功后通常最有机会降低个人 API 支出。
- **没有 GPU、调用量不稳定、每月只偶尔跑批**：先做调用控费、缓存复用和低价多模态 API A/B，通常比买硬件更划算。
- **需要极高精细的图片/视频判定**：采用本地优先 + API 难例兜底，而不是承诺完全离线；质量风险比 Token 更贵。

## 不要做的事

- 不把视觉分析关掉，也不把需要看图/视频的请求偷换为纯文本。
- 不把 `topic-label-hash-nb-v1` 当生产模型或自动放行依据。
- 不用 MiMo 伪标签训练出的模型绕过人工复核、Qwen3 查重和 CZ 终审。
- 不把真实数据、图片、视频、`.env` 或 API Key 复制到训练集、模型仓库、压测日志或报告。
- 不在未完成脱敏评测前替换生产默认模型或增加外部调用。
