# 召回盲标回流与自动训练

目标：让人工确认的召回与答复问题进入可回放、可验收的改进流程，而不是把盲标投票直接写进知识库或用于训练。

## 第一批改动：回流样本预览

- 管理员打开「召回标注 → 回流样本」。可按原候选归属品类筛选、逐批扫描，并回到原盲标详情核对。
- `GET /api/v1/blind-labeling/learning-samples/preview` 只允许具有 `retrieval:label_overview` 权限的账号访问。支持 `category_id`、`cursor` 和 `scan_limit`（默认 50、最多 100）。`next_cursor` 为空表示扫描到末尾；某页没有样本不代表已经扫完。
- 只预览未退池且已有最终结论的工单，包括全员一致、自动多数表决和历史仲裁。工单虽判可参考但没有候选过半时，只建议补证据，不指定某条知识。未选择的候选不当成负例；全不可参考但没有一致的结构化原因时，只建议补证据。分流是规则建议，不是事实认定。
- 预览返回内部工单 ID、候选知识 ID、结论类型、结构化原因计数、知识状态和证据摘要。快照核对的是候选的标题与正文，不保证发布范围、适用条件或索引状态相同。接口不返回问题原文、知识正文、标注人或自由填写文本。证据摘要用于发现预览所用的结构化证据变化，不是持久训练快照。
- 本批代码无迁移、无写入、无模型调用，也不会触发线上检索、GPU 训练或发布。管理员查看原盲标详情仍使用现有权限。

## 第二批改动：确认并保存样本

- 有 `retrieval:label_arbitrate` 权限的管理员可在「回流样本 → 复核样本」确认回放证据。这与工单投票结案分开，不再要求人工仲裁。排序问题从原候选选正确知识；漏召回和答复问题可指定原候选以外的正确知识。答复问题需填写脱敏后的预期要点。知识内容问题、缺知识和不纳入仍可记录，但不进入检索或答复回放队列。
- `GET` / `PUT /api/v1/blind-labeling/learning-samples/{work_order_id}/review` 只接受内部工单 ID。保存要求当前 `evidence_version` 及上次 `previous_review_id`（首次传 `null`）。后台重新核对后追加一版；已被别人复核、退池或证据变化均返回 409，不覆盖历史。
- 预览会复查证据及正确知识的版本。知识变更、失去发布状态或仲裁变化后，显示「证据有变 · 待重新确认」，不再具备回放资格。样本必须有原问题且引用已发布知识，才能确认进入回放。
- 安装前需升级 Alembic 至 `20261123_01_blind_review`（新增复核表，不改原盲标表）。预览列表不返回自由文本；人工录入的答复要点只在有复核权限的详情里返回，不发送给外部 AI。此批未启动任何回放或训练。

## 第三批改动：离线检索基线

从 `backend` 目录运行 `python -m scripts.replay_blind_label_retrieval <脱敏清单.json> --confirm-local-sanitized`。在运行进程设置 `BLIND_REPLAY_DATABASE_URL`（本地还原的 PostgreSQL 副本、建议使用只读账号）和 `BLIND_REPLAY_EMBEDDING_URL`（本机模型实例）。两者均须使用回环 IP，而不是生产隧道；应在网络隔离环境运行，模型及维度须与副本的向量索引匹配。副本需包含确认后的复核记录及对应知识、运行时配置和向量索引。

清单每次最多 100 单，显式指定工单内部 ID、预览中对应的复核版本 ID、人工复核的脱敏检索条件。不会从生产日志复制问题，不会默认按知识的品类或业务类型倒推原请求。

```json
{
  "cases": [{
    "work_order_id": "wo-example",
    "review_id": 1,
    "request": {
      "normalizedQuestion": "这类手机屏幕故障如何判断",
      "businessType": "self_operated",
      "categoryId": "example-category",
      "limit": 5
    }
  }]
}
```

- 复核失效、被排除或版本不符的样本跳过；模型不可用单列为未评估，不算召回失败。不会回退到原始工单文本。可选条件使用原入口字段：`productType`、`categoryId`、`brand`、`brandId`、`model`、`modelId`、`orderInfo`、`limit`、`candidatePoolLimit`。
- 回放复用 `/standard-search` 的语义排序和阈值过滤，不调用 HTTP 路由，不记录检索事件。数据库连接默认只读；报告只有内部 ID、排名、分数、阈值、结果状态及汇总，不含问题和答案正文。报告也应留在内部。
- 口径是**按知识来源分别排名**的检索窗口和返回 Top 3，不是插件重排后的排名；「不在窗口」不判断是筛选、索引还是召回的原因。答复问题样本只统计其检索环节，不评判最终回复。报告是副本的基线，不代表已实测生产表现。

## 第四批改动：最终答复离线验收

知识库的 `/standard-search` 只返回检索结果，Answer Hub 的草稿回放也不是线上助手的答复。这里的「最终答复」指**助手 Web 在检索、重排后向一线显示的推荐话术**，不是坐席最终发送给客户的消息。这条链路使用候选里的独立话术字段，不把知识标题和正文当成回复。验收脚本只汇总人工判定，不生成答复、不调用 Embedding 或外部 AI，也不写数据库或检索日志。

从 `backend` 目录运行。只需配置上一节约束下的只读 `BLIND_REPLAY_DATABASE_URL`，不要连接生产或通过回环隧道访问生产。清单最多 100 单、1 MB，版本字段使用内部版本标识；以下是格式示例，不是真实结果：

```json
{
  "baseline_version": "assistant-baseline-1",
  "candidate_version": "assistant-candidate-2",
  "cases": [{
    "work_order_id": "wo-example",
    "review_id": 1,
    "baseline": {"generation": "answered", "answer": "直接给出处理步骤。", "verdict": "incorrect"},
    "candidate": {"generation": "answered", "answer": "先确认适用条件，再给出对应步骤。", "verdict": "correct"}
  }]
}
```

1. 可先不填 `verdict`，用 `python -m scripts.replay_blind_label_answers <脱敏清单.json> --confirm-local-sanitized --review-references` 提取同版复核参考。此模式含预期要点，**只重定向到受控本地文件**，不发到日志、外部服务或 Git。
2. 审核员依据预期要点及对应知识判两版答复：`correct`、`incorrect` 或 `insufficient_evidence`（证据不足）；尽量不向审核员显示版本身份。没评就留空。正常跑完但没推荐话术记 `{"generation":"no_recommendation"}`，链路不可用记 `{"generation":"failed"}`，未拿到产物则留空整侧；三者都不等于答错。改动答复后需清除旧判定，重新审核。
3. 去掉 `--review-references` 生成统计报告。只有当前仍有效、且版本吻合的 `answer_issue` 复核才计入。两侧都判对错才进入配对正确率和提升/退步统计；单侧正确率仅基于该侧有判定的样本，不能直接相减。看正确率时同时看两侧未推荐、未评、缺证据、缺产物和执行失败计数，避免候选少推荐几单反而看起来更准；没有配对样本时差值为 `null`。报告不含答复正文和预期要点，也不据此自动判定发布或训练。

### 首批真实工单怎么收集

1. **选样本**：先在试点环境从一个高频品类选 10–20 个已确认的 `answer_issue` 工单，记录知识库内部工单 ID 和复核版本。保留同一批次的脱敏输入，不拷贝原始对话、真实用户身份或外部工单号。若助手接入要求数字工单号，每条使用专门分配的测试号；这个号不写入 `work_order_id`。
2. **锁定对照**：在隔离环境使用同一个知识快照和同一份输入，登记两套助手和检索配置的版本；只改这次要验收的参数或模型。知识库、重排、配置和反馈请求都必须由隔离服务接收或禁用，不能沿用线上配置或生产隧道。
3. **收集页面实际结果**：助手 Web 的 `web/business-adapter.js` 执行 `recommend`，`web/reply-view.js` 选择页面可见的卡片。不要把底层检索首条当成最终推荐。每单以复核针对的问题为准，记下页面最终显示的第一条对应且可复制的话术；多问题时不要拿另一问的话术评分。没有对应可复制话术就记未推荐。若本次要比较重排，需核对候选真的执行了目标重排；回退到基线排序的结果不能冒充候选，按该次对照执行失败记录。
4. **验收**：按前述命令取复核参考、填人工判定、生成去正文报告。首批只用来验证能否复现、是否有明显回归；不拿它触发训练或发布。真实样本和产物仅存受控目录，不进 Git。

## 后续三步的验收

1. **试点确认**：从现有完成单选约 100 单，覆盖一两个高频品类。AI 归因只能提交建议，调用前需确定脱敏和发送边界；没有依据的不进入训练集。
2. **离线回放**：用确认样本对比现网与候选改动，区分入池命中、Top 3 命中、最终答复正确率和误推荐。按主题分开优化样本与保留测试集，增加高分和无结果对照工单。被确认缺知识的走补录审核，不把它归为排序失败。候选侧调用不得写生产检索日志或触发自动作业。
3. **训练候选**：达到样本数、品类覆盖和独立评测门槛后，才在离线环境触发训练。正确知识入池但排序落后，试重排；正确知识进不了池且已排除知识缺失和规则拦截，再考虑现有 Embedding LoRA Runner。训练结果只登记为候选，上传、替换生产模型及全量向量重建分别审批，不由训练完成事件触发。

## 一键运行隔离回流试点

从 `backend` 目录在**断网、无生产隧道**的环境执行（路径为运维提供的受控目录）：

```powershell
python -m scripts.run_blind_learning_cycle --confirm-local-sanitized `
  --scan-limit 50 --ai-limit 5 --out <仓库外受控目录>\cycle-01.json
```

- `BLIND_REPLAY_DATABASE_URL` 指向已迁移的回环 PostgreSQL 副本。运行使用只读快照，不写复核、检索日志或知识。默认一页扫描 50 单；产物的 `discovery.next_cursor` 用于下一页。
- 配置 `BLIND_CYCLE_OLLAMA_URL`（例如 `http://127.0.0.1:18114`）与 `BLIND_CYCLE_OLLAMA_MODEL` 后，本地 AI 可给待复核项分类。AI 只接收白名单内的理由代码、票数和位置，不接收工单 ID、问题正文、知识文本、自由备注或人员信息。AI 的建议不改结案结果，也不自动确认样本。模型调用失败时仍保留规则建议，不能视作 AI 已完成。
- 要运行检索验证，另加 `--retrieval-manifest <人工复核且脱敏的清单.json>`，设置 `BLIND_REPLAY_EMBEDDING_URL` 并核对模型和向量维度。重放逐单复核版本，只在同一知识来源及既有过滤条件和阈值下衡量候选。答复部分可另加 `--answer-manifest`，它自动汇总已有人工判定，不负责生成推荐话术或自动打分。
- **自动训练的首个候选是轻量重排，不是 Embedding LoRA。** 只有检索清单完整评估后才检查训练门槛。相同规范化问题和目标知识不能跨越训练/留出集；至少需要 10 条带明确负例的训练工单、10 条留出工单，训练和留出各至少覆盖 3 条目标知识。未选候选、内容已变化的候选不当负例。算法在训练集拟合标题词组重合权重，并要求留出集 Top 3 命中提高且目标名次无退步，才输出本地候选权重；排不到阈值内窗口的知识不会因重排被找回。小样本通过不等于线上可用，仍需独立评测。
- `knowledge_drafts` 只对已确认且证据仍有效的知识缺口或内容问题排出**待编辑任务**。添加 `--knowledge-inbox <仓库外受控目录>\editor.sqlite3` 可将任务写入持久隔离队列。相同版本重复运行不会新增任务；复核不再有效且工单仍出现在当前扫描页时，旧任务标记为 `superseded`，编辑前仍应复核证据。每个隔离副本独立使用一个 SQLite 文件。任务不猜应该修改哪篇知识，不生成无依据的正文，不导入或发布知识；此出口尚未接入线上知识工作台。
- 控制台只输出计数。文件含内部工单 ID 和证据版本，须放在仓库外受控目录并且不覆盖旧产物。没有真实复核清单时可以先做发现；不能把发现数量、连通性探测或测试样本写成真实回放或训练结果。

### 真实投票影子验证（不依赖原工单正文）

```powershell
python -m scripts.run_blind_vote_shadow --confirm-isolated-replica `
  --out <仓库外受控目录>\frozen-vote.json `
  --editor-inbox <仓库外受控目录>\editor.sqlite3
```

- 仅用于断网副本。使用已经投满、无历史人工仲裁的工单，候选必须仍已发布且标题和内容与冻结快照一致。只学习明确可参考或不可参考的绝对多数票；未点选不是反例。数据库内部用问题摘要去重，文件不带问题摘要、原文、知识内容或投票人。

### 准备真实漏召回与答复复核

从 `backend` 目录在断网副本执行，继续使用只读 `BLIND_REPLAY_DATABASE_URL`：

```powershell
python -m scripts.prepare_blind_replay_intake --confirm-isolated-replica `
  --pages 50 --per-lane 20 --cross-order-hints `
  --review-inbox <仓库外受控目录>\recall-review.sqlite3 `
  --out <仓库外受控目录>\review-intake-01.json
```

- 清单只选已投满、无历史人工仲裁、尚未复核或复核已失效的工单。所有冻结候选都过半不可参考的进入漏召回**待查**；恰有一条仍为同版的候选过半可参考的进入最终答复**待查**。两种都不输出训练标签。按品类分配名额，优先保留有池外线索的漏召回项；`has_more=true` 表示本次未扫完。答复待查只供核验，不是已确认答错。
- 池外线索来自同品类、同规范化问题的其他已投满工单，来源文章须获绝对多数可参考、仍已发布且标题与内容和冻结快照一致；该文章未出现在待查工单的冻结候选中。标题和内容一致不等于适用范围、筛选条件或索引状态一致。输出不含问题原文、问题摘要、知识正文、投票人或原始请求。
- 可选 `--review-inbox` 仅把入选且有池外线索的漏召回项登记进 `offline_recall_review_queue`。它和待编辑队列、复核表、回放清单分开。重复运行不新增相同证据；本次**确实预览到**的工单若线索失效或证据变更，旧任务标记为 `superseded`。未预览到、或只因限额没被选中的，不据此判失效。每个副本使用独立队列，核验前仍须复查工单与知识的当前版本。
- 2026 年 11 月 25 日隔离副本试跑：扫描 3,005 单，漏召回与答复各入选 20 单；9 单具有池外线索，已登记为 `awaiting_evidence`，重跑新增 0 条。这 9 单**未确认漏召回**。下一步从「回流样本 → 复核样本」核对知识是否适用于对应问题和业务条件，并准备已复核的脱敏检索输入；对答复待查，还要拿到两版实际推荐及独立判定。复核确认后才使用前文脚本执行真实回放。
