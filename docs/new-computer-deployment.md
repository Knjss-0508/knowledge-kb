# 新电脑（GPU 节点）部署：架构决策记录

> 状态：**已定稿并落地**
> 落地日期：2026-09-22
> 实际部署步骤见 [`docs/gpu-embedding-tunnel.md`](./gpu-embedding-tunnel.md)

---

## 一、结论（先看这里）

**新电脑只跑两样东西：嵌入模型服务 + SSH 反向隧道。数据库、后端、网站全部留在旧服务器。**

```
        新电脑（GPU 节点）                        旧服务器
  ┌──────────────────────────┐          ┌──────────────────────────────┐
  │  embedding-qwen 容器      │          │  kb-backend 容器              │
  │  （RTX 4060 + CUDA）      │          │  PostgreSQL 18 + pgvector     │
  │           ▲              │          │  nginx + 网站                 │
  │           │ :80           │          │           ▲                   │
  │  SSH 反向隧道容器         │          │           │ 127.0.0.1:18080   │
  └───────────┼──────────────┘          └───────────┼───────────────────┘
              │                                      │
              └────── ssh -R 0.0.0.0:18080 ──────────┘
                     （新电脑主动连旧服务器 22 端口）
```

后端通过 `http://host.docker.internal:18080/v1` 调用嵌入服务，**对后端而言完全透明** ——
它不知道模型在另一台机器上。

## 二、被否决的方案（原文档写的那个）

原 `new-computer-deployment.md` 描述的是**把整套业务栈搬到新电脑**：
后端、worker、媒体网关都搬过去，只把数据库留在旧服务器。

**这个方案已否决。** 原因是一条容易忽略的账：**业务代码每次查库都要跨网络。**

### 实测数据

| 链路 | 单次往返 |
|---|---|
| 新电脑 → 旧服务器 **直连 TCP 22** | **32 ms** |
| 新电脑 → 旧服务器 **经 Tailscale DERP 中继** | **351 ms**（慢 11 倍） |

一次知识召回请求要查好几次库（查询向量、候选检索、分类过滤、适用性过滤、
媒体地址解析……），**每一次都要多走一个 351 ms 的往返**。
按 3~5 次计算，光网络就吃掉 1 秒以上，而目前整条召回链路的目标是 100 ms 级。

**为什么走 DERP 中继而不是直连**：新电脑在对称 NAT 之后，旧服务器的腾讯云 EIP
又阻断了入站 UDP，两边打不了洞，Tailscale/WireGuard 只能退化到 DERP 中继。
这是网络环境的硬限制，不是配置问题。

### 两套方案对比

| | 原方案（架构 Y） | 最终方案（架构 X） |
|---|---|---|
| 新电脑跑什么 | 后端 + worker + 媒体网关 + 嵌入 | **只有嵌入服务 + 隧道** |
| 数据库位置 | 旧服务器 | 旧服务器（不变） |
| 每次查库的代价 | **跨网络，+351 ms/次** | 本机，0.3 ms |
| 网站位置 | 新电脑（需改 DNS、证书、入口） | 旧服务器（不变） |
| 家庭宽带中断的影响 | **整个网站不可用** | 召回质量降级，网站照常可读 |
| 旧服务器资源 | 只留数据库 | 保留全部（仅嵌入容器停用） |
| 迁移风险 | 高（要动 DNS / 证书 / 媒体 / 入口） | 低（后端只改一个环境变量） |

关键判断：**瓶颈是嵌入推理（GPU），不是后端逻辑。** 只把 GPU 那一段搬走，
就能拿到 84% 的性能收益，而不用承担跨网络查库的代价。

## 三、新电脑上跑什么、不跑什么

| 组件 | 在新电脑上？ | 说明 |
|---|---|---|
| `embedding-qwen`（TEI + CUDA） | ✅ **跑** | 唯一需要 GPU 的组件 |
| SSH 反向隧道容器 | ✅ **跑** | 把嵌入服务暴露给旧服务器 |
| `kb-backend` | ❌ 不跑 | 留在旧服务器，避免跨网络查库 |
| PostgreSQL | ❌ 不跑 | 数据**一定**留在旧服务器 |
| nginx / 网站 | ❌ 不跑 | 留在旧服务器 |
| 媒体网关 | ❌ 不跑 | 留在旧服务器 |
| 后台 worker | ❌ 不跑 | 留在旧服务器 |

新电脑上的容器只有两个，`docker ps` 应该长这样：

```
kb-embedding-qwen     Up (healthy)    ghcr.io/huggingface/text-embeddings-inference:cuda-1.8.3
kb-embedding-tunnel   Up              alpine:3.20
```

## 四、常见误解

**❌「要把数据库搬到新电脑」**
不要。数据留在旧服务器是这套方案的**前提**，不是妥协。搬过去反而会让
每次查库多走 351 ms。

**❌「新电脑要装 PostgreSQL / 要装数据库管理工具」**
不需要。新电脑上没有数据库。查数据用旧服务器上的 Adminer
（见 [`docs/postgres-web-admin.md`](./postgres-web-admin.md)）或桌面客户端直连。

**❌「网站也要跟着搬」**
不搬。网站继续在旧服务器上由 nginx 提供，用户无感知。

**❌「隧道方向是旧服务器连新电脑」**
反了。**新电脑主动连旧服务器**的 22 端口，用 `ssh -R` 建反向隧道。
这正是这套方案能绕开对称 NAT 的原因。

**❌「旧服务器上的嵌入容器可以删了」**
**不要删。** `kb-embedding-qwen` 容器在旧服务器上保留为 **CPU 兜底**，
新电脑关机或网络故障时可以一键回滚：

```bash
# 旧服务器上执行（回滚到 CPU 嵌入）
docker start kb-embedding-qwen
# 并把后端的 EMBEDDING_BASE_URL 改回 CPU 容器地址后重建后端
```
