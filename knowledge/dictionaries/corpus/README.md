# 知识库术语语料

本目录是「知识库的说法」与「检索词库的说法」之间的对齐基线。

| 文件 | 内容 | 来源 |
| --- | --- | --- |
| `knowledge-titles.json` | 知识库业务知识（总部标准 + 业务沉淀）的标题与自带同义问法 | 导出 Excel |
| `standard-items.json` | 知识库「关联标准项」清单（它自己的规范勾选项路径） | 导出 Excel |
| `build-from-export.cjs` | 从导出 Excel 生成上面两个文件 | 自研 |
| `map-standard-items.cjs` | 比对「标准项」与「词库」，列出未映射术语 | 自研 |
| `refresh-corpus.cjs` | 旧的爬取脚本（检索接口按问法反查），已被导出流程取代 | 自研 |

## 为什么需要它

`standard-retrieval-lexicon.js` 的别名表要同时覆盖两套说法：

- **同事的说法**：日常口语，如「屏幕碎了」「进水了」。
- **知识库的说法**：知识条目的规范用词，如「主屏碎裂/磕点/掉漆/气泡」「浸液情况」「偏光检测」。

只覆盖前者会出现「问的是 A、召回的是 B」——实测「偏光膜破损」会召回「保护膜破损」，
因为词典里有「膜/破损」但没有「偏光」这一知识库用词。

本语料就是知识库用词的来源，也是防止术语再次脱节的回归基线。

## 怎么刷新（推荐：导出全量）

知识库的导出接口一次给出全量业务知识，且自带「关联标准项」——
那是知识库自己的规范勾选项路径，比标题更干净。

```bash
# 1) 登录后取导出文件（需要知识库账号；不要把账号写进仓库）
#    GET /api/v1/knowledge/export/excel?status=published  ->  xlsx
# 2) 生成语料与标准项清单
node knowledge/dictionaries/corpus/build-from-export.cjs <导出.xlsx>
# 3) 看词库还差哪些术语
node knowledge/dictionaries/corpus/map-standard-items.cjs
```

2026-10-20 的执行结果：导出行 **19521**，其中业务知识
（知识来源 = 总部标准 / 业务沉淀）**1200 条**（生效中 871 / 待审核 329）；
标准项路径 754 条 + 业务沉淀场景项 352 条。

### 为什么不再用检索接口爬（`refresh-corpus.cjs`）

1. **覆盖度取决于探针写得好不好**：576 次请求只爬到 527 条，靠旧语料合并才凑到 760 条，
   而实际有 1200 条 —— 语料残缺会让覆盖度虚高（414 条时曾显示 100%）。
2. **列表接口 `/api/v1/knowledge` 有分页缺陷**：按 `created_at` 排序，同秒记录顺序不稳定，
   翻页会静默跳过约 31% 的记录（19544 个 ID 只拉到 13454 个，抽样直查确认缺失 ID 真实存在）。
3. **导出接口没有这些问题**：一次给全，且带 `关联标准项`。

`refresh-corpus.cjs` 保留作为备用（例如导出接口不可用时），但**不要再拿它的产物当覆盖度基线**。

## 导出表头（列 → 用途）

```
A 知识ID   B 主题键        C 记录ID  D 知识键      E 主标题   F 副标题
G 知识内容 H 知识来源      I 业务类型 J 知识分类    K 录入方式 L 关联标准项
M 适用范围 N 生效状态      O 来源版本 P 变更类型    Q 创建类型 R 失效类型
S 失效原因 T 来源追溯      U 校验备注
```

三个关键字段：

- **`H 知识来源`** = `机型配置信息`(18321) / `总部标准`(847) / `业务沉淀`(353)。
  **只有后两者是业务知识**；`机型配置信息`是系统生成的机型参数，不属于术语语料。
- **`F 副标题`** = 知识库自带的同义问法（换行分隔）。这是「知识库的说法」最直接的来源。
- **`L 关联标准项`** = 知识库的规范勾选项路径。两种形态：
  - 总部标准：多行 `【模块】-【子项】-【叶子】`，如 `【基本情况】-【机型】`
  - 业务沉淀：单行 `场景：X；部件；现象；适用类目：Y`，如
    `场景：标准判定；屏幕；息屏黑屏状态下屏幕顶部出现一条红线；适用类目：笔记本`

### 两个坑（都会静默出错）

1. **业务沉淀行的「主标题」是空的**，标题实际在 `B 主题键` 里（353 条全如此）。
   只读 `E 主标题` 会丢掉业务沉淀全部 353 条。
2. **`E 主标题` 为空的 353 行，恰好就是业务沉淀** —— 这不是数据缺失，是导出格式如此。

## 怎么用（补词流程）

1. 跑 `map-standard-items.cjs`，看「未映射片段」清单。
2. 挑**有标题/副标题佐证**的词补进 `standard-retrieval-lexicon.js`
   （没有佐证的不要加——凭印象加词正是历史上脱节的原因）。
3. 跑 `node --test tests/*.test.cjs`，重点看：
   - `lexicon-kb-mapping.test.cjs`：新词可识别 + 有佐证 + 覆盖度与映射率不倒退
   - `lexicon-coverage.test.cjs`：覆盖度阈值
4. 覆盖度下降说明语料里出现了新术语，回到第 1 步。

## 覆盖度是怎么算的

`tests/lexicon-coverage.test.cjs` 用本语料度量「知识标题能被词典锚定」的比例。

| 时间 | 语料 | 覆盖度 | 说明 |
| --- | --- | --- | --- |
| 2026-10-19 | 414 条 | 100% | **假象**：语料残缺，只含检索接口能反查到的知识 |
| 2026-10-19 | 760 条 | 95% | 按品类爬取后，仍缺 440 条业务知识 |
| 2026-10-20 | 1200 条 | 89.2% → **97.8%** | 换成导出全量，暴露真实差距后补齐 |

测试阈值设在 **0.95**（防退化线）。注意：这个比例是相对「本语料」的，
而本语料已覆盖知识库全部业务知识，所以它现在能代表真实水平。

## 映射率是怎么算的

`map-standard-items.cjs` 把标准项拆成片段（模块名/子项/叶子，或场景项的部件/现象），
统计词库能识别多少。2026-10-20 基线：**1347 个片段，已映射 1186（88.0%）**。

未映射的剩余片段主要是：

- 过泛的词（`来源`/`其他情况`/`通用`/`有`/`无`/`缺失`）——**故意不收**，
  收了会让任何问句都命中「功能检测」类目；
- 阈值描述（`有斑数量≤15且直径≤20mm`）——不是术语，无法映射成单词；
- 长尾专有名词（`A2700`/`A3529` 等机型代号）。

## 旧脚本 `refresh-corpus.cjs` 的两个坑（保留备查）

### 必须逐品类爬（踩过的坑）

**品类决定候选集**：`productType` 不同，知识库返回的候选集不同。
早期版本固定用 `productType: '手机'`，576 次请求只爬到 414 条，
**缺了 346 条**——笔记本/平板/游戏机等品类专属的知识一条都拿不到
（例如 `A-19483 笔记本屏幕固定单条线状显示异常…`）。
现在的 `refresh-corpus.cjs` 会遍历 `['手机','笔记本','平板','智能手表','耳机','相机','游戏机','台式机']`。

### 两个接口约束（都会导致静默失败）

1. **`requestId` 必须只生成一次**：知识库要求 Header `X-Request-Id` 与正文
   `requestId` 完全一致，分别调用 `Date.now()` 会直接 `400 REQUEST_IDENTITY_MISMATCH`。
2. **候选可能在「顶层 `candidates`」**：知识库对某些 `knowledgeOrigin`
   只把结果放在顶层 `candidates`，`reply`/`standard` 都是 `false`。
   只读两个池会大量漏抓。

刷新时注意：

1. 只用**只读**检索接口（`POST /api/v1/integration/standard-search`），不要触发任何写入。
2. **低并发**（建议 ≤4）、控制轮数，避免影响生产（线上同一时刻有同事在用）。
3. 候选的 `text` 字段是**截断**的（实测 414 条里 364 条长度为 0，最长 189 字），
   不要依赖它做术语提取；可靠来源是完整的 `title` 与 `keywords`。
4. 集成密钥不要写入仓库；从部署环境变量或历史提交里临时读取。
5. **必须逐品类爬**，且同时读顶层 `candidates` 与 `reply`/`standard` 两个池（原因见上）。
